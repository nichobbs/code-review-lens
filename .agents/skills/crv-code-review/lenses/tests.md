# Tests lens

Checks whether the tests would fail if the changed code were wrong. Runs when tests change, or when tested source changes with no test change.

## Using the Behavioral Test Matrix (`<scratch>/layers.json`)

Before reading raw test files line by line, inspect `testMatrix` in `<scratch>/layers.json` (generated by `scripts/prepare_pr.mjs`):

- Each entry lists the extracted `describe`/`it` behaviors, `assertions` count, `verifiedTargets`, and two automated flags:
  - `hollow: true` — the test block has `0` assertions (`expect`/`assert`).
  - `mockOnly: true` — every assertion in the test block only checks mock calls (`toHaveBeenCalled` / `toHaveBeenCalledWith`) rather than inspecting a returned value or state change.
- Prioritize inspecting test cases flagged `hollow: true` or `mockOnly: true`, and compare the list of extracted `cases[].behavior` against the production changes in `layers.contracts` and `layers.flows` to spot missing unhappy paths without getting lost in AI-generated mock boilerplate.

## Looks for

- A changed behaviour with no test that covers it. Grep for the test of each changed function.
- A logic change inside an untested function of 50 or more lines, in a diff that changes no test. Ask for a characterization test, or for the changed logic in a tested function of its own. Exceptions: lines added at the end of the function, and trivial edits.
- The revert question: for each new test, would it fail if the production change were reverted?
- A test that passes when the code is wrong (`hollow: true` or `mockOnly: true`): no assertion, an assertion on a mock instead of the result, or a snapshot of the wrong thing. An expected value or call order copied from the implementation, so the test repeats the code. Exceptions: characterization tests and documented snapshots.
- A mock that replaces the code under test, so the test checks the mock.
- A test that reaches past the module's interface into its internals. The interface is the test surface.
- Unhappy paths: the error, empty and boundary cases of the change with no test.
- A test that depends on time, order or shared state, and can pass or fail between runs.
- A test change that makes CI pass with no code fix: a new `.only`, a `.skip` with no issue link, a raised timeout, a looser threshold, or a deleted assertion.

## Never reports

- Tests for trivial code: types, constants, plain wiring.
- Coverage percentages. A number says nothing about whether the assertions check behaviour.
- Test style that no repository standard states.

## Severity

- `medium`: a changed behaviour with no test, or a test that cannot fail.
- `low`: a missing unhappy-path case, or a test that reaches past the interface.
- Never `high` on its own, except for a committed `.only`, because the rest of the suite stops running. When the untested code is also wrong, the correctness lens reports the defect.

## Evidence

- Name the changed function and the test file you searched, or the test that cannot fail, as `path:line`.
- For a test that cannot fail, say which change to the code would leave it passing.
